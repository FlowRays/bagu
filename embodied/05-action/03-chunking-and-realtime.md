# Action chunking 与实时性

> 两个问题其实是一个：**大模型跑得慢，而机器人要高频闭环。** chunking 是主要答案。

## 1. Action chunking：一次预测 H 步

不是每个控制周期预测一个动作，而是**一次预测未来 $H$ 步**（典型 $H=8\sim50$），然后依次执行。

来自 **ACT**（Action Chunking with Transformers）。

### 为什么能缓解 compounding error

模仿学习的经典问题：模型每步都有小误差 → 进入训练分布外的状态 → 误差更大 → 雪崩。误差累积大致随步数**平方级**增长。

chunking 把决策频率从每步一次降到每 $H$ 步一次，**决策点少了 $H$ 倍**，累积误差自然小得多。

$$\boxed{\text{chunk 越长，越接近开环；越短，越接近逐步闭环}}$$

### 为什么能缓解多模态

单步动作的分布高度多模态（这一瞬间往左往右都行），但**整段轨迹**的分布模式更少更清晰（"从左绕"是一整条轨迹）。在 chunk 层面建模，模型不容易在相邻两步之间左右摇摆。

$$\boxed{\text{逐步预测容易在模式之间抖动，chunk 级预测天然一致}}$$

## 2. Temporal ensembling

chunk 之间硬切换会在接缝处跳变。ACT 的做法是**重叠 chunk + 加权平均**：

```text
t=0  预测 [a0 a1 a2 a3 a4 ...]
t=1  预测    [a1'a2'a3'a4'...]
t=2  预测       [a2''a3''...]
                 ↓
实际执行 a2 = w0·a2 + w1·a2' + w2·a2''
```

权重通常用指数衰减 $w_i\propto e^{-m\cdot i}$，**越新的预测权重越大**。

好处：动作平滑、隐式做了多次预测的集成、降低单次预测的方差。
代价：每个控制周期都要跑一次推理（失去了 chunking 省算力的好处），只保留了它对误差累积和多模态的好处。

## 3. chunk 长度的取舍

| $H$ 小 | $H$ 大 |
|---|---|
| 闭环快，对扰动反应及时 | 开环久，中途环境变了来不及反应 |
| 决策点多，误差累积重 | 决策点少，误差累积轻 |
| 多模态抖动明显 | 轨迹一致性好 |
| 推理频率高 | **推理频率低，算力友好** |

实践上和任务动态性有关：静态桌面操作可以 $H$ 大，有人干扰或物体会动的场景要 $H$ 小。

## 4. 实时性：三个频率要分清

$$\boxed{\text{控制频率} \ \gg\ \text{推理频率},\qquad \text{chunk 把两者解耦}}$$

| 频率 | 典型值 | 谁决定 |
|---|---|---|
| **控制频率** | 100–1000 Hz | 底层控制器（阻抗/位置环） |
| **动作频率** | 10–50 Hz | policy 输出动作的速率 |
| **推理频率** | 1–10 Hz | 模型跑一次的速度 |

一次推理产出 $H$ 步动作，以动作频率依次下发；底层控制器再在两个动作之间做插值，跑到控制频率。

## 5. 让大模型跑得动的手段

| 手段 | 做法 |
|---|---|
| **action chunk** | 一次推理管 $H$ 步，摊薄成本（最重要） |
| **小 action expert** | 大 backbone 跑一次，小 expert 跑 K 步迭代 |
| **flow matching 代替 diffusion** | 采样从 50 步降到 1–10 步 |
| **异步推理** | 执行当前 chunk 的同时后台算下一个 chunk，隐藏延迟 |
| **量化 / 蒸馏** | 权重量化减少读取字节；蒸馏成小模型 |
| **缓存视觉特征** | 相邻帧视觉变化小时复用部分计算 |

### 异步推理的关键细节

```text
执行 chunk_k 的第 1..H 步
        │
        └─(并行) 用第 1 步时的观测算 chunk_{k+1}
                  → 算完时已经过了 Δ 步
                  → 必须丢掉 chunk_{k+1} 的前 Δ 步再接上
```

**没对齐这个延迟偏移**是实际部署里很常见的 bug：动作会滞后，表现为"总是慢半拍"或抖动。

## 6. 和 LLM 推理优化的对照

| | LLM | VLA |
|---|---|---|
| 瓶颈 | decode 是 memory-bound | 同样是 memory-bound，但**有硬实时约束** |
| 一次产出 | 1 个 token | **H 步动作**（chunk） |
| 加速主线 | batching 提吞吐 | **降延迟**，batch 通常是 1 |
| 投机解码 | 有效（小 batch 场景） | 思路可迁移，但动作是连续的，验证准则要重新定义 |

$$\boxed{\text{LLM 服务优化吞吐，机器人优化延迟 —— 目标不同，手段的优先级就不同}}$$

## 自测

**1.** action chunking 是什么？它为什么能缓解 compounding error？

> **答：** 一次预测未来 $H$ 步（典型 8~50）然后依次执行，来自 ACT。
> 模仿学习的误差累积大致随步数**平方级**增长；chunking 把决策频率降到每 $H$ 步一次，**决策点少了 $H$ 倍**，累积误差自然小得多。

**2.** 为什么 chunk 能缓解多模态抖动？

> **答：** 单步动作分布高度多模态（这一瞬间往左往右都行），逐步预测容易在相邻两步之间左右摇摆；而**整段轨迹**的模式更少更清晰（"从左绕"是一整条轨迹），在 chunk 层面建模天然保证一致性。

**3.** temporal ensembling 怎么做？代价是什么？

> **答：** **重叠 chunk + 加权平均**：每个控制周期都重新预测一个 chunk，同一时刻的动作由多个 chunk 的预测加权平均得到，权重按指数衰减 $w_i\propto e^{-mi}$，**越新的预测权重越大**。
> 好处是动作平滑、隐式集成、降方差。**代价是每个周期都要推理一次**，失去了 chunking 省算力的好处，只保留了对误差累积和多模态的好处。

**4.** chunk 长度怎么取舍？

> **答：** $H$ 小：闭环快、对扰动反应及时，但决策点多、误差累积重、多模态抖动明显、推理频率高。
> $H$ 大：开环久、中途环境变了来不及反应，但决策点少、轨迹一致性好、**算力友好**。
> 和任务动态性有关：静态桌面操作可以大，有人干扰或物体会动就要小。

**5.** 三个频率分别是什么？chunk 在其中起什么作用？

> **答：** **控制频率** 100–1000 Hz（底层控制器）、**动作频率** 10–50 Hz（policy 输出速率）、**推理频率** 1–10 Hz（模型跑一次）。
> chunk **把推理频率和动作频率解耦**：一次推理产出 $H$ 步，以动作频率依次下发，底层控制器再插值到控制频率。

**6.** 异步推理的关键细节是什么？不处理会怎样？

> **答：** 执行当前 chunk 的同时后台算下一个 chunk，但**算完时已经过了 $\Delta$ 步**，所以必须**丢掉新 chunk 的前 $\Delta$ 步**再接上。
> 不处理这个延迟偏移，动作会滞后，表现为"总是慢半拍"或抖动 —— 这是实际部署里很常见的 bug。

**7.** LLM 推理优化和 VLA 推理优化的目标差别？

> **答：** **LLM 优化吞吐**（batching 是主线），**VLA 优化延迟**（batch 通常是 1，有硬实时约束）。
> 两者的 decode 都是 memory-bound，但 LLM 一次产出 1 个 token、VLA 一次产出 H 步动作。投机解码的思路可迁移，但动作是连续的，接受/拒绝的验证准则要重新定义。
